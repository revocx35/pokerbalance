# Architecture

## Components

```
browser / installed PWA ──HTTPS──► [reverse proxy, optional] ──HTTPS──► container: uvicorn + FastAPI ──► SQLite (/data)
```

| Path | Role |
| --- | --- |
| `app/__main__.py` | Entry point. Creates the self-signed cert (ECDSA P-256, 10 years, fingerprint logged) and starts uvicorn with TLS. |
| `app/config.py` | All settings from `POKER_*` env vars; version string. |
| `app/main.py` | App factory. `Guard` ASGI middleware (security headers, body cap, per-IP API rate limit, same-origin + JSON-only check for writes, client IP from trusted proxies). Serves the static shell. |
| `app/api.py` | JSON API under `/api`: session/setup, account + TOTP, players (admin), groups, games. Auth via dependencies `current` / `admin`. |
| `app/auth.py` | argon2id hashing, login `Throttle`, server-side sessions, TOTP, first-run setup token. |
| `app/games.py` | Game state transitions (finish, deal, reopen, rounding), game JSON view, group summary. |
| `app/payouts.py` | Pure money math: pot split, deal prefill, rounding ladder. |
| `app/settle.py` | Pure "who pays whom" solver. |
| `app/whatsapp.py` | Optional: sends game results to WhatsApp through a wa_logger API token (outbound HTTPS client, token encryption, message builder, background dispatch). |
| `app/db.py` | SQLite schema + migrations (`PRAGMA user_version`), connection + `BEGIN IMMEDIATE` transactions. |
| `app/static/` | Vanilla-JS SPA (`app.js`), CSS, manifest, service worker, icons (generated by `tools/make_icons.py`). |

## Data model

- `users` (also the players; `is_admin`, `must_change_pw`, `disabled`, TOTP secret + last used step)
- `sessions` (SHA-256 of the token, CSRF token, created/last seen)
- `groups`, `group_members`
- `games` (`buy_in` cents, `payout_bp` JSON list of basis points, `status` running/finished,
  `finish_kind` last_standing/deal, `round_stack` JSON)
- `game_players` (`buy_ins`, `bust_seq`, `place`, `deal_bp`, `base_payout`, `payout`)
- `transfers` (from, to, amount, paid)
- `wa_config` (one row: wa_logger address, AES-GCM-sealed API token, optional certificate pin), `wa_sends` (last send result per game),
  `groups.wa_mode/wa_chat_id/wa_auto`, `users.wa_chat_id` (migration v2)

**Money is integer cents, percentages are integer basis points** (100% = 10000) everywhere, so
nothing is lost to floating point. The UI formats them.

## Key design decisions

- **Places are derived while running.** Only the bust order (`bust_seq`) is stored; the k-th of N
  players to bust is in place N−k+1. Rebuys, undo and late players therefore never need place fix-ups.
  Places and payouts are written when the game finishes.
- **Pot split** uses largest remainder at whole currency units (`allocate`), leftovers to the largest
  share, so the payouts always sum exactly to the pot.
- **Deal:** the admin sends a share (bp) for every player; must sum to 10000. Prefill = busted players
  in paid places keep their structure %, the rest is chopped evenly among players still in. Remaining
  players are ranked by deal share for places.
- **Rounding** (`payouts.round_more`): walks a ladder of nice steps (1, 2, 5, 10, 20, 25, 50, 100,
  200, 250, 500, …). The first step is the largest nice step ≤ half a buy-in (100 buy-in → 50s), each
  "round more" takes the next step that changes something. Each step re-splits the *current* payouts
  with largest remainder; ties go to the smaller payout (the user's example 250/150 → 200/200).
  Guards: total unchanged, no winner drops to 0, step never above the smallest prize. A stack of
  previous payouts in `games.round_stack` makes *Revert* exact. `base_payout` keeps the unrounded value.
- **Settlement** (`settle.settle`): bitmask DP finds the maximum number of zero-sum groups among
  non-zero balances (≤15 people exact; minimal transfers = n − groups). Inside each group every
  minimal solution is a tree with a leaf, so a memoized search over "settle one person completely"
  moves enumerates them all and keeps the roundest (score per amount: 100s > 50s > 10s > 5s > whole).
  Groups > 8 people or a blown search budget fall back to greedy. Transfers are regenerated whenever
  payouts change (paid flags reset).
- **Group "still to pay"** nets all unpaid transfers per player and runs the same solver.
- **No framework in the UI** and no inline script/style, so the CSP can be `script-src 'self'; style-src 'self'`.
  DOM is built with a small `h()` helper (text nodes only → no HTML injection).
- **Polling:** the running-game view re-fetches every 8 s (skipped while typing, a dialog is open or
  the deal maker has unsaved edits), so players following on their phones see buy-ins and busts.
- **Service worker:** network-first for the app shell, cache as offline fallback; `/api/*` is never cached.

## Platform constraints

- Single process, single container; SQLite in WAL mode. Login throttle and API rate limit state is
  in memory (reset on restart) — fine for a home deployment.
- PWA install + service worker need a secure context: a trusted certificate (reverse proxy) or
  `localhost`. With the self-signed cert the app works in the browser but is not installable.
- `__Host-` cookies require HTTPS; `POKER_COOKIE_SECURE=false` exists only for local HTTP development.

## Threat model

Assets: the admin account (can change every result), players' accounts (read access to their
groups), the game history / who-owes-whom data.

Attackers considered: anyone on the internet who can reach the URL; a signed-in non-admin player;
a malicious site the admin visits while signed in; someone on the LAN path.

| Threat | Mitigation |
| --- | --- |
| Claiming the admin account on a fresh install | First-run setup needs a random token from the container log / `data/setup-token`; setup endpoint throttled; token single-use. |
| Password guessing / credential stuffing | argon2id (64 MiB, t=3); per-account lockout after 5 failures (15 min, doubling up to 24 h, also for non-existent names); per-IP (20/15 min) and global limits; dummy hash for unknown users; one generic error message. Optional TOTP 2FA with replay protection. |
| Default/weak passwords | No default account; minimum 10 characters; admin-created users get a random temporary password and must change it before anything else. |
| Session theft / fixation | 256-bit random token, only its SHA-256 stored; `__Host-` cookie, `Secure; HttpOnly; SameSite=Strict`; new session on every login (old one deleted); idle (7 d) and absolute (30 d) timeouts; logout deletes the row; "sign out everywhere"; password change/reset and disabling a user kill sessions. |
| CSRF | Per-session CSRF token required in `X-CSRF-Token` on every authenticated write (constant-time compare); writes must be `application/json`; `Origin` must match `Host` and `Sec-Fetch-Site` must be same-origin when present; SameSite=Strict. |
| XSS / clickjacking | Strict CSP without inline code; DOM built from text nodes; `X-Frame-Options: DENY` + `frame-ancestors 'none'`; `nosniff`; `Referrer-Policy: no-referrer`. |
| Privilege escalation | Every write endpoint requires admin; members only read groups they belong to (others return 404); last admin can't be demoted, disabled or deleted. |
| Spoofed client IP to dodge limits | `X-Forwarded-For` only honoured from `POKER_TRUSTED_PROXIES`, right-most untrusted hop used. |
| Eavesdropping | TLS by default (self-signed, or custom cert); HSTS; recommended deployment keeps the proxy→app hop on HTTPS and firewalls the port to the proxy. |
| Resource abuse | 64 KiB request body cap; pydantic limits on every field (lengths, list sizes, numeric ranges, extra fields rejected); 600 API requests/min per IP; uvicorn concurrency cap; settlement search budget. |
| Container breakout impact | Non-root uid 10001, read-only rootfs, `cap_drop: ALL`, `no-new-privileges`, pids/memory limits; only port 8443. |

### WhatsApp results (outbound, optional)

The admin connects a [wa_logger](https://github.com/revocx35/wa_logger) API token (Account → WhatsApp). The token can only
list the chats its creator chose and send text to them; it cannot read messages. When a game ends (last player standing or a deal) and
the group's mode is *group* (one WhatsApp group) or *dm* (each player gets the results and only their own payments), a background
thread sends the message; the outcome is shown on the game with a "Send again" button (needed after rounding payouts, because the
automatic message goes out the moment the game ends). DMs are spaced 2–4 s apart.

| Threat | Mitigation |
| --- | --- |
| Token theft from the database or a backup | Stored AES-GCM-encrypted with `data/wa.key` (0600, outside the DB file); never returned by the API (only "connected"), never logged. Worst case a stolen token sends text to the few chats it was created for. |
| Token sent over a bad channel | `https://` only; certificate verified with the system CAs, or (self-signed LAN server) pinned by SHA-256 fingerprint; TLS ≥ 1.2; no redirects followed; 10 s timeout; 256 KiB response cap. The connection is proven (destination list fetched) before anything is saved. |
| SSRF through the address field | Admin-only; just `https://host[:port]` (no path, credentials or query); link-local (cloud metadata), unspecified and multicast addresses are never contacted; private LAN addresses are allowed on purpose. |
| Chat ids injected by a client | A group's or player's chat must be one the token lists (checked at save time), format-validated; wa_logger enforces its own allowlist again. |
| Message-text injection | Names have control characters and WhatsApp formatting marks stripped; text capped at 4000 characters. |
| Players seeing others' WhatsApp chats | Chat ids are returned to admins only. |

Known limits: rate-limit state is in memory; TOTP secrets are stored unencrypted in the SQLite file
(protect `data/`, mode 600); the only outbound network calls are the optional WhatsApp ones above.
